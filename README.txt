# GPPAF research source code

Source code for **GPPAF (Geometry–Process–Path–Automation Framework)** for wire arc additive manufacturing of complex multi-hole components. The release implements the four methodological components described in the accompanying manuscript—**TC-DSFNet, PA-HGTS, PA-LCCS and HELS-DP**—and includes executable comparison methods, process-data preparation, fixed reviewer inputs, archived TC-DSFNet five-fold checkpoints with implementation-version metadata, a PA-HGTS training-reference run with explicit train/validation provenance, numerical tests and manuscript-to-code traceability.

The repository is organized for direct technical inspection and reproducibility: each methodological component is linked to executable code, fixed inputs/configuration, saved verification outputs and manuscript-to-code documentation.

## Reviewer quick start

```bash
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
# Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pytest -q
python scripts/verify_release.py
python scripts/verify_claims.py
python examples/run_all.py --output runs/examples
```

The checks require no network service, Unity installation, robot, or GPU after dependencies are installed. The exact CPU package versions used for the bundled verification outputs are in `requirements-tested.txt`; see `docs/ENVIRONMENT.md`.

## 1. TC-DSFNet process design

The package contains **200 single-layer rows, 250 multilayer mean-response rows and 1,050 layerwise rows (105 process conditions × 10 layers)**. `data/processed/layers.csv` preserves all five process variables plus factor, varied X value, source filename and source-row number. `data/processed/layer_condition_metadata.csv` provides one auditable five-parameter record for each of the 105 layerwise conditions.

The metadata uses the common single-factor base setting **80 A, 26 cm/min, 3 Hz, 3 mm** recorded in the supplied process-design tables. For the current/speed/frequency/amplitude layerwise sweeps, the v12 figure protocol specifies **60 s** interpass cooling. For the cooling-time sweep, cooling time is the varied factor and the other four variables use the common base setting. The exact map and its evidence basis are stored in `data/layer_settings.json` and `data/processed/layer_settings_provenance.json`.

The Eq. (2) branch modulation is implemented directly as `gamma * c + beta`, with identity initialization `gamma=1, beta=0`. The single-layer and multilayer branches remain four- and five-dimensional, respectively.

The current implementation follows manuscript Eq. (6) by averaging the trend-violation terms once over the complete retained relationship set `C`. The v1.4.5 executable training example under `reference_results/examples/` was regenerated with this corrected implementation. The grouped five-fold checkpoint/results directory under `reference_results/cross_validation/` is retained as an **archived v1.4.4 artifact set** and is explicitly version-labelled; it is not presented as output generated by the v1.4.5 Eq. (6) implementation. Its recorded configuration is 100 epochs, seed 2026 and M=256 candidates, with archived Best-of-M values of **2.637% single-layer** and **5.516% multilayer**. Fresh five-fold outputs for the current code can be regenerated with the commands below. The manuscript Fig. 7 reference values (**2.82% / 6.59%**, 24.2% reduction versus the best comparison) are retained in `reference_results/process_comparison/manuscript_reported_figure7.json` for traceability.

```bash
python scripts/cross_validate.py --epochs 100 --candidates 256 --output runs/cross_validation
python scripts/benchmark_process_cv.py --cv-run runs/cross_validation \
  --epochs 100 --candidates 256 --output runs/process_comparison
python scripts/verify_claims.py --process-cv runs/cross_validation \
  --process-comparison runs/process_comparison
```

The comparison driver evaluates **RSM, SVR, RF, cVAE, Affine-cINN and TC-DSFNet** on the same saved grouped test folds. The comparison driver exports per-sample, per-fold and aggregate outputs for direct verification of the six-method comparison and the 24.2% summary statistic.

## 2. PA-HGTS continuous path planning

PA-HGTS builds the sparse heterogeneous candidate graph, applies hard geometric/graph constraints, performs learned second-order candidate scoring and constrained beam search, and applies feasibility-preserving local reconnection. Eq. (35) weights, Eq. (36) `gamma`, Eq. (37) positive regret weight, local-search depth and ACO budget are explicit command-line parameters rather than hidden benchmark constants.

A compact executable six-method check is bundled with the training-reference checkpoint:

```bash
python scripts/benchmark_paths.py --instances reference_results/path_benchmark_example/instances.json \
  --checkpoint reference_results/pa_hgts_training_reference/model.pt \
  --beam 16 --lambda-cost 1.0 --lambda-bound 0.1 \
  --failure-penalty 1000 --local-cost-weight 1.0 \
  --local-rounds 2 --local-top-edges 8 \
  --aco-ants 6 --aco-iterations 5 --aco-evaporation 0.2 \
  --seed 2026 --output runs/path_example
```

The bundled training-reference run is produced by `scripts/train_hgts.py` on 20 explicit training instances and selected against 8 disjoint validation instances with seed 2026; its inputs, manifest and histories are stored under `reference_results/pa_hgts_training_reference/`. `data/path_validation_100.json` contains the **100-case evaluation set** spanning three cross-section families, three problem-size classes and multiple grid phases. `configs/fig10_release_protocol.json` records the fixed benchmark defaults. The same `benchmark_paths.py` driver evaluates NN, ACO, G-beam, P-beam, R-GLS and PA-HGTS on any supplied evaluation set/checkpoint pair, keeps every failed run in the success-rate denominator, applies the declared failure penalty, and exports aligned per-instance and statistical results.

## 3. PA-LCCS local curvature-continuous smoothing

Adjacent duplicate removal and short-segment screening are separate operations. Only numerically coincident adjacent coordinates are deduplicated, while `SmoothConfig.epsilon_L` is used solely as the minimum segment-length threshold in Algorithm 1; short but distinct segments and the original path endpoints are preserved. Candidate corners are screened by segment length, turning angle and discrete curvature; smoothing windows depend on bead width, local segment length, boundary clearance and neighboring-window distance. Accepted local polylines are replaced by quintic Bézier curves subject to curvature, geometric-deviation, feasible-region and intersection constraints. A rejected local replacement retains the corresponding original polyline, followed by final global feasibility verification.

## 4. HELS-DP multilayer connection

HELS-DP enumerates entry/exit/direction states for within-layer components, retains connector geometry in the DP labels, and performs interlayer dynamic programming with predecessor backtracking. Feasible transitions combine distance, direction and local heat-accumulation terms. The released local heat implementation uses Gaussian spatial decay and exponential cooling and is documented as the implementation used by this release, rather than as an extra manuscript equation.

## Data integrity and figure-level evidence

Raw source CSVs are hashed in `data/manifest.json`. `scripts/verify_release.py` verifies source hashes, 105×10 layer completeness, row lineage, Eq. (2), environment consistency, the fixed 100-case path input, PA-LCCS certificates and HELS-DP backtracking. `scripts/verify_claims.py` reports packaged verification results together with the corresponding manuscript reference claims.

For long-term article archiving, large experimental records and figure-level numerical outputs can be mirrored to the article data DOI. `docs/ARTICLE_SOURCE_DATA.md` lists the recommended records for Fig. 7, Fig. 10, FEA, point-cloud analysis and automation I/O.
